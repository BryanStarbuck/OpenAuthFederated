Going to production means pointing your app at a live OpenAuthFederated instance, federating to your identity provider(s), stating your admission policy, and turning on the revocation controls that make the platform safe. The examples use an organization-only app restricted to the `corp.example` Google Workspace; a public app states `signUpMode: 'public'` instead (see [Admission](../apis/frontend/admission.mdx)).

**Implemented in code.** The SAML connection (SP metadata / ACS URL / Entity ID and assertion validation) is in `~/BGit/Bryan_git/OpenAuthFederated/code/packages/auth-backend/src/saml.ts` — `samlSpMetadata()`, `buildSamlClient()`, `validateSamlAcs()`. The app's admission policy runs at sign-in in `~/BGit/Bryan_git/OpenAuthFederated/code/packages/auth-backend/src/frontend.ts` — `createFederatedFrontend()`, inner `admit()` / `finishSignIn()`, then the app's `resolveGrants` hook (default `defaultResolveGrants()`) — with permission checks in `~/BGit/Bryan_git/OpenAuthFederated/code/packages/auth-backend/src/permissions.ts`.

## 1. Switch to live keys and a custom domain

Production uses `*_live_*` keys and your own auth/API hostnames. Set these in your hosting provider's environment configuration (never commit secrets).

```env
NEXT_PUBLIC_AUTH_PUBLISHABLE_KEY=pk_live_your_publishable_key
AUTH_SECRET_KEY=sk_live_your_secret_key

NEXT_PUBLIC_AUTH_FRONTEND_API=https://auth.corp.example
AUTH_BACKEND_API=https://api.corp.example/v1
```

Configure DNS so the Frontend API resolves at `auth.corp.example` and the Backend API at `api.corp.example`, each served over HTTPS only. (These are app-side variables; the embedded library itself reads no environment variables.) See [Environment variables](./environment-variables.mdx) for the full list.

## 2. Register a SAML / OIDC connection to Google Workspace

OpenAuthFederated is the Service Provider; Google Workspace is the Identity Provider. SAML 2.0 via a Google Workspace custom app is the go-forward default; OIDC is an acceptable equivalent with the same domain restriction.

**SAML 2.0 (recommended):**

1. In OpenAuthFederated → **Connections → New SAML connection**, copy the SP **ACS (Assertion Consumer Service) URL** and **Entity ID**.
2. In the Google Admin console → **Apps → Web and mobile apps → Add custom SAML app**.
3. Paste the ACS URL and Entity ID; download Google's IdP metadata (or copy the SSO URL, Entity ID, and X.509 certificate) back into OpenAuthFederated.
4. Configure attribute mapping: `email`, `first_name`, `last_name`, and a **groups** attribute so memberships flow through.
5. Turn the app **ON for everyone** (or the relevant Org Units) in Google.

**OIDC (alternative):** register OpenAuthFederated as an OAuth client in Google, set the redirect URI to your callback, and request the `openid email profile` scopes. On this path the platform verifies the hosted-domain (`hd`) claim and `email_verified` on every sign-in.

## 3. State your admission policy

The app states who may sign in through the API — the library ships no domains and reads no
environment variables. For an organization-only app:

```ts
createFederatedFrontend({
  sessionSecret,
  requirePolicy: true,
  signUpMode: 'restricted',
  restrictions: { allowlist: true, blocklist: true },
  allowlistIdentifiers: ['*@corp.example'],
  blocklistIdentifiers: appConfig.blockedEmails,          // exact emails; the more specific match wins
  connections: [{ strategy: 'oauth_google', clientId, clientSecret, redirectUri,
    allowedHostedDomains: ['corp.example'], hostedDomainHints: ['corp.example'] }],
})
```

With this:

- Only verified `@corp.example` addresses pass, and on the Google path the verified `hd` claim must be `corp.example`.
- An unverified email is refused (`identity_email_unverified`); an off-list one with `identity_not_allowlisted`.
- Nothing about the policy is published by `/environment`.

A public app instead states `signUpMode: 'public'` (optionally with a blocklist). Run
`evaluateAdmission()` at boot with one positive and a few negative identities so a misconfigured
policy fails loudly. Full reference: [Admission](../apis/frontend/admission.mdx).

## 4. Map groups to roles and enable MFA

- **RBAC:** in **Authorization**, map upstream groups → roles → `<feature>:<action>` permissions (for example `code:read`, `docs:write`, `*:read`). The IdP's groups are inputs; the authoritative model lives in our own backend/DB. These are the permissions your [route protection](./protect-routes.mdx) and `has()` checks evaluate.
- **MFA:** MFA is inherited from the upstream Google Workspace IdP — enforce 2-Step Verification in the Google Admin console. For sensitive actions, enable **optional step-up reverification** in OpenAuthFederated so the user must re-authenticate before the action proceeds.

## 5. Confirm session and security behavior

The hybrid session model is on by default in production:

- **Short-lived JWT access token** (Bearer) for stateless verification.
- **Rotating, HttpOnly refresh cookie** with `SameSite` set for CSRF defense — never stored in `localStorage`.
- **Server-side session records** so a session can be revoked immediately despite the short token lifetime.
- HTTPS only, CSP headers, and full audit logging of sign-in / sign-out / refresh / permission-denied / admin actions. No end-user passwords are ever stored.

## 6. Offboarding and revocation

When an employee leaves, suspend or delete their Google Workspace account. Access is cut off promptly through three layers working together:

1. **SCIM deprovision** — the `user.deleted` (or suspend) event removes the user from OpenAuthFederated and fires your webhooks.
2. **Short token lifetime** — the existing access token expires quickly and cannot be refreshed once the upstream account is gone.
3. **Force-revoke** — the app calls `frontend.revokeUserSessions(email)` (needs a `sessionStore`) to invalidate every active session for a user immediately, without waiting for token expiry; adding the address to `blocklistIdentifiers` keeps it out.

## Production checklist

- [ ] Live `pk_live_*` / `sk_live_*` keys set; secret key server-only.
- [ ] `auth.` and `api.` custom domains serving HTTPS.
- [ ] Google Workspace SAML (or OIDC) connection registered and attribute/group mapping verified.
- [ ] Admission policy stated (`requirePolicy: true`) and checked at boot with `evaluateAdmission()`.
- [ ] Groups mapped to roles and `<feature>:<action>` permissions.
- [ ] MFA enforced upstream; step-up reverification configured for sensitive actions.
- [ ] Webhook signing secret set; SCIM deprovision tested with a suspend.
- [ ] Force-revoke verified from the admin dashboard.
