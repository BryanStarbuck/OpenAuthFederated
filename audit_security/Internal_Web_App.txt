1. 10-month session lifetime AND 10-month inactivity timeout (idle expiry effectively disabled)  [MEDIUM] [MISUSE]

SITUATION / PROBLEM:
buildAuthFrontend() hardcodes BOTH the session maximum lifetime and the inactivity timeout to 10 months and passes them to createFederatedFrontend(). Setting the inactivity timeout equal to the maximum lifetime means an idle (or stolen) session never ages out early — it lives the full ~300 days.

ROOT CAUSE:
Deliberate product policy ("a signed-in user stays signed in for 10 months ... NOT logged out overnight, on idle") implemented as sessionTtlSeconds = inactivityTimeoutSeconds = TEN_MONTHS_SECONDS. This contradicts the library contract (default sessionTtl 7d; "Apps setting years-long values weaken captured-session risk") and the app's own .env.example warning: "Session lifetime bounds (Finding 6) — do NOT restore ~10-year / no-timeout values. Absolute maximum lifetime (default 14 days) and sliding idle timeout (default 8 hours)." The library's default idle timeout (~12h) is overridden up to 10 months, neutralizing the idle-timeout defense.

SCENARIO:
An attacker obtains the oaf_act3hub_session cookie (laptop malware, a synced/backed-up browser profile, a copied disk-store record, or any future XSS). Because the cookie stays valid for 10 months with no idle expiry, the attacker keeps authenticated access for up to ~300 days without the victim ever using the account; the only kill switch is an admin explicitly running revoke-user, which nobody triggers because nothing looks wrong.

RISK:
A captured/stolen session cookie remains a valid credential for up to ~300 days; idle-timeout containment ("an abandoned laptop logs itself out") is gone.

REPRO STEPS:
1. Sign in. 2. Copy the oaf_act3hub_session cookie value. 3. Leave the session idle for weeks. 4. Replay the cookie from a fresh client against /api/... — readSession() only rejects past expireAt (10mo) or a lastActiveAt gap > inactivityTimeoutSeconds (also 10mo), neither of which trips, so it still mints access tokens.

SOURCE FILES INVOLVED:
- App: /Users/bryan/BGit/all/app/code/packages/backend/src/modules/auth/auth-frontend.ts:154-166 (TEN_MONTHS_SECONDS; sessionTtlSeconds and inactivityTimeoutSeconds both = TEN_MONTHS_SECONDS), :207-223 (passed into frontendConfig).
- App guidance it violates: /Users/bryan/BGit/all/app/code/packages/backend/.env.example (the "Finding 6 ... do NOT restore ~10-year / no-timeout values" block).
- Library enforcement point: /Users/bryan/BGit/Bryan_git/OpenAuthFederated/code/packages/auth-backend/src/frontend.ts:603-611 (defaults), :766-780 (readSession expiry/inactivity checks).

CALL COUNT:
1 configuration site (auth-frontend.ts buildAuthFrontend).

FIX:
App side (root cause): decouple the two knobs. Restore a real sliding idle timeout (e.g. inactivityTimeoutSeconds 8-24h, matching the library intent and the .env.example guidance) and cap sessionTtlSeconds well below 10 months (e.g. 14-30 days), or make both env-overridable (AUTH_SESSION_TTL_SECONDS / AUTH_INACTIVITY_TIMEOUT_SECONDS, already documented in .env.example) with safe defaults. If a long "remember me" is a hard product requirement, gate it behind a shorter idle timeout so activity re-slides it but abandonment expires it. Library side: no change required (defaults are already sane).

2. requireHostedDomain not enabled on a Google-Workspace-gated app  [MEDIUM] [MISUSE]

SITUATION / PROBLEM:
The internal app's canonical access rule (OpenAuthFederated CLAUDE.md "Reference deployment") is that a user MUST be an active member of the company Google Workspace (whitehatengineering.com) — Workspace is the single source of truth. But buildAuthFrontend() never sets requireHostedDomain, so it defaults to false in the library. With it false, the sign-in tail accepts an identity whose email DOMAIN is on allowedDomains even when the Google hosted-domain (hd / Workspace-membership) claim is absent.

ROOT CAUSE:
The Google connection is built with hostedDomain intentionally unset ("Leave hostedDomain unset so either company domain is accepted; allowedDomains enforces") and requireHostedDomain is never passed. The code conflates "email ends in act3ai.com/whitehatengineering.com" with "is a Workspace member." Per the library, when requireHostedDomain is false a verified email on an allowlisted domain passes without the hd claim (frontend.ts:1189-1213).

SCENARIO:
Any path that yields a Google-verified email on an allowlisted domain without Workspace membership authenticates. The app has removed the one control (hd enforcement) that guarantees "Workspace member only," so a non-Workspace Google identity presenting a verified allowlisted-domain email, or an identity whose Workspace membership was suspended but whose email assertion persists, is not reliably excluded. It also weakens offboarding: Workspace suspension is meant to be authoritative, but the app is not keying on the Workspace (hd) signal.

RISK:
Authentication no longer strictly requires Google Workspace membership; the "Workspace is the single source of truth" guarantee in the charter is not enforced at the library boundary.

REPRO STEPS:
1. Present a Google OIDC id_token with email_verified=true and email on an allowlisted domain but no hd claim. 2. finishSignIn() computes presentedDomain from the email domain (because requireHostedDomain is false) and admits the session.

SOURCE FILES INVOLVED:
- App: /Users/bryan/BGit/all/app/code/packages/backend/src/modules/auth/auth-frontend.ts:142-151 (google connection; hostedDomain unset; no requireHostedDomain), :207-223 (frontendConfig omits requireHostedDomain).
- Library behavior: /Users/bryan/BGit/Bryan_git/OpenAuthFederated/code/packages/auth-backend/src/frontend.ts:216-222 (requireHostedDomain doc, default false), :1189-1213 (hd-vs-email enforcement).
- Charter requirement: /Users/bryan/BGit/Bryan_git/OpenAuthFederated/CLAUDE.md "Reference deployment" (Workspace membership required).

CALL COUNT:
1 configuration site (auth-frontend.ts).

FIX:
App side (root cause): set requireHostedDomain: true in frontendConfig so an identity without an allowlisted hd (Workspace) claim is rejected even when its email domain matches. Since both allowed domains are Workspace domains this is a safe tightening; expose it as an env override (e.g. AUTH_REQUIRE_HD, default true) if a non-Workspace domain is ever needed. Optionally also pin GOOGLE_HOSTED_DOMAIN for the single-domain case.

3. Webhook auth forks the library verifyWebhook and omits timestamp/replay protection  [MEDIUM] [MISUSE]

SITUATION / PROBLEM:
The @Public POST /api/webhooks/auth endpoint mutates the local user store (create/update/DELETE from event.data). It authenticates the request with a hand-rolled HMAC-SHA256 of the RAW body only. The library exports verifyWebhook, which verifies HMAC-SHA256 over `${timestamp}.${rawBody}` — binding a timestamp so a captured request cannot be replayed. The app does not use verifyWebhook and includes no timestamp/nonce, so there is no replay defense; a single captured valid webhook can be replayed indefinitely. The hand-rolled scheme is also incompatible with the library's signing format, so a genuine library-signed webhook (timestamp.rawBody) would fail this verifier.

ROOT CAUSE:
Reimplementation of webhook verification instead of calling the library's verifyWebhook. createHmac("sha256", secret).update(raw) covers only the body; there is no timestamp extraction, no freshness window, and no reuse of the library canonicalization. (Positives: it correctly uses req.rawBody rather than a re-serialized body, and compares in constant time, and fails closed when the secret is unset — Finding 12 of the prior pass.)

SCENARIO:
With AUTH_WEBHOOK_SIGNING_SECRET configured, an attacker who observes one valid signed user.deleted (or user.updated) request — via a proxy log, a mirrored request, or a leaked example — can POST the exact same body+signature repeatedly at any later time to re-trigger user-store mutations (e.g. repeatedly delete/downgrade a user), because nothing ties the signature to a moment in time.

RISK:
Replayable state-changing webhook (user create/update/delete); divergence from the library means a real library-signed webhook would be rejected (correctness), and the security-relevant canonicalization is now maintained in two places that can drift.

REPRO STEPS:
1. Configure AUTH_WEBHOOK_SIGNING_SECRET. 2. Capture one valid {body, x-webhook-signature} pair. 3. Re-POST it hours/days later — verifySignature() recomputes HMAC over the same raw body, matches, and the handler re-applies the mutation.

SOURCE FILES INVOLVED:
- App: /Users/bryan/BGit/all/app/code/packages/backend/src/modules/webhooks/webhooks.controller.ts:37-74 (handler), :76-109 (verifySignature — HMAC over req.rawBody only, no timestamp).
- Library API not used: /Users/bryan/BGit/Bryan_git/OpenAuthFederated/code/packages/auth-backend/src/index.ts:6 (exports verifyWebhook); client.ts verifyWebhook (HMAC over `${timestamp}.${rawBody}`).

CALL COUNT:
1 verifier (webhooks.controller.ts verifySignature), 1 handler route.

FIX:
App side (root cause): replace the hand-rolled verifySignature with the library's verifyWebhook, passing the RAW body bytes (req.rawBody — already available via rawBody: true in main.ts) plus the timestamp and signature headers, and reject stale timestamps outside a small window (e.g. 5 min). This restores replay protection and keeps one canonicalization in the library. Keep the existing fail-closed-when-secret-missing posture. Library side: document verifyWebhook's expected header names so the app forwards the right timestamp/signature headers.

4. Privileged local-only routes gate on a spoofable Host header, not the socket address  [MEDIUM] [APP-BUG]

SITUATION / PROBLEM:
GET /api/open/vscode spawns a detached OS process (opens a filesystem path in an editor) and is "protected" by isLocalhostRequest(req), which derives the host from req.hostname / req.headers.host. Both are client-controlled. The same spoofable check gates the /api/health/auth-config disclosure. A caller who can reach the server but is NOT on the loopback interface can set Host: localhost and pass the gate.

ROOT CAUSE:
The loopback determination reads the HTTP Host header (req.hostname falls back to the Host header when trust proxy is off) instead of the real transport peer address (req.socket.remoteAddress). Host is attacker-supplied and unrelated to which interface the connection arrived on.

SCENARIO:
If this app is exposed beyond loopback (deployed, port-forwarded, or reachable on a LAN — CLAUDE.md describes it as an employee hub, i.e. potentially served to others), an authenticated employee (any valid company token clears the global JwtAuthGuard; the route is a GET so it clears deny-by-default RBAC) sends GET /api/open/vscode?path=~/... with header Host: localhost. isLocalhostRequest returns true and OpenService.openInVsCode spawns a process on the SERVER for any path inside the server user's home directory. On win32 the spawn uses shell:true, widening the surface. Even confined to home, this is server-side process execution / file access driven by a remote request. auth-config likewise leaks credentialsFilePresent to non-local callers.

RISK:
Remote-triggered process spawn and home-directory file access on the server host (open route); server-config disclosure (auth-config) — both gated only by a forgeable header.

REPRO STEPS:
1. From a non-loopback client with a valid token: curl -H "Host: localhost" -H "Authorization: Bearer <token>" "https://<server>/api/open/vscode?path=~/". 2. isLocalhostRequest passes; the server spawns the editor process.

SOURCE FILES INVOLVED:
- App: /Users/bryan/BGit/all/app/code/packages/backend/src/modules/open/open.controller.ts:7-17 (isLocalhostRequest on req.hostname/headers.host), :40-45 (gate then spawn); /Users/bryan/BGit/all/app/code/packages/backend/src/modules/open/open.service.ts:65-79 (spawn; win32 shell:true).
- Same pattern: /Users/bryan/BGit/all/app/code/packages/backend/src/modules/health/health.controller.ts:11-22, :81-83.

CALL COUNT:
2 isLocalhostRequest implementations (open.controller.ts, health.controller.ts).

FIX:
App side (root cause): base the loopback decision on the transport peer, not the Host header — check req.socket.remoteAddress (and req.ip only when trust proxy is correctly configured) against 127.0.0.1 / ::1 / ::ffff:127.0.0.1, rejecting anything else. Do NOT trust Host/X-Forwarded-Host for a security decision. Apply to both open.controller.ts and health.controller.ts. Additionally, prefer shell:false on win32 (pass executable + args array) to drop the shell surface, and consider making the /open route unavailable unless an explicit "local desktop mode" flag is set.

5. No per-app token audience set, so aud-based cross-app isolation is unused  [LOW] [MISUSE]

SITUATION / PROBLEM:
buildAuthFrontend() never sets audience, and auth.strategy.ts calls federatedClient.verifyToken(token) with no audience option. The library's aud binding — the mechanism that stops one app from accepting another app's token — is therefore entirely unused. Isolation here rests only on each app having a distinct on-disk sessionSecret plus a distinct issuer ("act3-internal-app") and cookiePrefix.

ROOT CAUSE:
audience is an opt-in footgun: the library only enforces aud when the app passes it on BOTH mint and verify. This app passes it on neither.

SCENARIO:
Today the distinct per-app secret makes cross-app token acceptance impossible, so this is defense-in-depth only. But if a future deployment ever shares a signing secret between two OpenAuthFederated apps (a common loadOrCreateSecret path, or a migration to a shared JWKS issuer), the absence of an audience claim would let each app accept the other's tokens. The isolation currently depends on an implicit invariant (secrets never shared) rather than an explicit aud check.

RISK:
Low today (secrets differ); a latent cross-app token-confusion risk if secrets/issuers are ever shared.

REPRO STEPS:
N/A operationally today; verify by inspection — no audience in frontendConfig (auth-frontend.ts) and no audience passed to verifyToken (auth.strategy.ts:50).

SOURCE FILES INVOLVED:
- App: /Users/bryan/BGit/all/app/code/packages/backend/src/modules/auth/auth-frontend.ts:207-223 (no audience); /Users/bryan/BGit/all/app/code/packages/backend/src/modules/auth/auth.strategy.ts:50 (verifyToken with no audience).
- Library: /Users/bryan/BGit/Bryan_git/OpenAuthFederated/code/packages/auth-backend/src/frontend.ts:211-215 (audience doc/footgun), verify.ts:169 (audience enforced only when supplied).

CALL COUNT:
1 mint config site, 1 verify call site.

FIX:
App side: set a distinct audience (e.g. "act3-internal-app") in frontendConfig AND pass { audience: "act3-internal-app" } to federatedClient.verifyToken(token) in auth.strategy.ts, so aud is bound on both mint and verify. This makes cross-app isolation explicit and survives any future secret/issuer sharing.

7. resolveGrants never wired: every real Google user is read-only, admin/write routes unreachable  [LOW] [APP-BUG]

SITUATION / PROBLEM:
buildAuthFrontend() passes no resolveGrants to createFederatedFrontend(), so the library's defaultResolveGrants runs: role "employee", permissions []. Under REAL Google sign-in every user therefore has zero permissions. All permission-gated routes — social-media:write (probe), users:manage (admin offboarding revoke-user), and any *:write film/movies/tools actions — are unreachable in production. Only the localhost dev mock (DevAuthCore) hands out *:write and org:admin, so those features appear to work only in dev.

ROOT CAUSE:
The Workspace-group -> role/permission mapping the charter calls for is never implemented on the app side; the library default (least-privilege, fail-closed) is left in place. This is a fail-closed correctness gap, not an over-grant.

SCENARIO:
An admin signs in with real Google to offboard a departing employee (POST /api/sessions/revoke-user) and receives 403 because their token carries no users:manage permission — offboarding cannot be performed through the UI in production. Same for running a social probe or any write action.

RISK:
Not privilege escalation (it fails closed), but a real functional/authorization gap: administrative and write capabilities are inoperable under real auth, which pressures operators toward unsafe workarounds (enabling the dev mock, or later hardcoding elevated grants — which WOULD be a vuln).

SOURCE FILES INVOLVED:
- App: /Users/bryan/BGit/all/app/code/packages/backend/src/modules/auth/auth-frontend.ts:207-223 (frontendConfig omits resolveGrants).
- Library default: /Users/bryan/BGit/Bryan_git/OpenAuthFederated/code/packages/auth-backend/src/frontend.ts:458-472 (defaultResolveGrants — empty permissions), :246-247 (resolveGrants hook).
- Consumers that become unreachable: /Users/bryan/BGit/all/app/code/packages/backend/src/modules/sessions/sessions.controller.ts:52-53 (users:manage), /Users/bryan/BGit/all/app/code/packages/backend/src/modules/social-media/social-media.controller.ts:41-43 (social-media:write).

CALL COUNT:
1 missing configuration site (affects all permission-gated routes).

FIX:
App side (root cause): implement resolveGrants(identity) that maps the verified identity's Google Workspace groups/roles to this app's permissions (e.g. members->write, admins->users:manage), keeping the authoritative model in the app, and pass it into frontendConfig. Continue to fail closed for unknown groups. Do NOT hardcode elevated grants or trust client-supplied roles.
