1. Per-app token isolation via `audience` (and `issuer`) is documented but NOT enforced in embedded verification  [HIGH]

SITUATION / PROBLEM:
The `audience` config option is documented as the mechanism that binds a token to one app "so two apps sharing a secret/prefix cannot accept each other's tokens" (frontend.ts config doc). In embedded mode the mint side DOES stamp `aud` on the session cookie and the access token, but the verify side never enforces it: createFederatedFrontend() calls configureEmbeddedVerification({ sessionSecret, issuer }) WITHOUT the audience, and verifyToken() only applies an audience check when the caller passes `opts.audience` on each call. The EmbeddedVerificationConfig interface has no `audience` field at all. Issuer has the same shape: it is forwarded to configureEmbeddedVerification, but is optional, and minted tokens fall back to the constant issuer "openauthfederated" when the app sets none — so two apps that both omit `issuer` also share an issuer.

ROOT CAUSE:
The single bridge between minting and verifying (configureEmbeddedVerification) carries `sessionSecret` and `issuer` but not `audience`, and verifyToken defaults audience to "unset" rather than to the configured value. The documented guarantee lives only in the mint path.

SCENARIO:
Two sibling apps are (mis)configured to share one sessionSecret (a plausible mistake, since the docs frame audience — not a distinct secret — as the isolation control, and both apps default issuer to "openauthfederated"). App A mints an access token for user U with roles for A. That exact token verifies successfully at App B, because B's verifyToken enforces neither aud nor a distinct iss. U now carries A's grants into B.

RISK:
Cross-app token acceptance / privilege bleed whenever a secret is shared, and a false sense of isolation for any team that followed the docs and set only `audience`. The actual protection today is a DISTINCT per-app sessionSecret; audience adds nothing. Likelihood is moderate (depends on a shared secret), impact is high (authn/authz crossing an app boundary).

REPRO STEPS:
1. Configure App A and App B with the same sessionSecret and per-app `audience` ("app-a" / "app-b"), no explicit issuer.
2. Sign in to App A, capture the minted access JWT (aud="app-a").
3. Present it as a Bearer token to App B's protected route (authenticateRequest / getRequestAuth with B's options).
4. Observe it verifies and yields A's claims — B never checked aud or iss.

/Users/bryan/BGit/Bryan_git/OpenAuthFederated/code/packages/auth-backend/src/frontend.ts (lines 211-215 config doc claiming the guarantee; 665 configureEmbeddedVerification call omitting audience; 711, 864 mint sets aud only when cfg.audience present)
/Users/bryan/BGit/Bryan_git/OpenAuthFederated/code/packages/auth-backend/src/verify.ts (lines 22-29 EmbeddedVerificationConfig has no audience; 160-172 embedded branch only sets audience from opts; 174-194 JWKS branch same)

CALL COUNT:
2 mint sites stamp aud (signSession, mintAccessToken in frontend.ts) but 0 verify sites enforce it by default. The one bridge that could carry it (configureEmbeddedVerification, frontend.ts:665) omits it.

FIX:
* Root cause: the mint/verify bridge drops audience; verify defaults it off.
* How: make audience a first-class part of embedded verification config and enforce it by default.
* Structure: add `audience` to EmbeddedVerificationConfig; have configureEmbeddedVerification receive and store it; have verifyToken default `verifyOpts.audience` to `embeddedVerification.audience` (and default issuer enforcement on) when the caller does not override.
* Files changed: verify.ts (extend interface + apply the configured audience/issuer as defaults in both branches); frontend.ts (pass `audience: cfg.audience` into the configureEmbeddedVerification call at line 665, and require a non-default issuer when audience isolation is requested). Also update the config doc so it no longer promises isolation the code does not deliver, and steer callers to a distinct per-app sessionSecret as the primary control.

2. Grants are resolved once at sign-in and never re-resolved; deprovision / role-change latency equals the session lifetime  [HIGH]

SITUATION / PROBLEM:
resolveGrants(identity) runs exactly once, in finishSignIn, and the resulting roles/permissions are baked into the session record (cookie + optional store). Every subsequent access token is minted FROM that stored grant set (mintAccessToken → grantsForOrg reads session.roles/permissions). Nothing re-runs resolveGrants or re-checks upstream group membership on token mint. So when a user is demoted or offboarded upstream (their Workspace group is removed), their already-established session keeps minting access tokens with the OLD elevated grants until the session hits max lifetime or (only if a store is configured) the inactivity timeout.

ROOT CAUSE:
The session record is the authoritative grant source after sign-in; there is no re-resolution hook and, in embedded mode, no deployed backend to call sessions.verify against.

SCENARIO:
An admin is removed from the "engineering-admins" Workspace group at 09:00. Their browser session was established yesterday with a 7-day max lifetime and no store (so no inactivity cutoff). Until the max lifetime expires — up to 7 days — every /tokens mint still emits org:admin permissions. They retain admin access for a week after being deprovisioned.

RISK:
Delayed deprovisioning of privilege — the core promise of "offboarding revokes access promptly" is bounded only by session lifetime, not by the upstream change. Impact high for admin roles; likelihood high (group changes are routine).

REPRO STEPS:
1. Sign in; get org:admin grants baked into the session.
2. Remove the user from the mapped upstream group.
3. Without signing out, call POST /client/sessions/:id/tokens.
4. Observe the freshly minted token still carries org:admin.

SOURCE FILES INVOLVED:
/Users/bryan/BGit/Bryan_git/OpenAuthFederated/code/packages/auth-backend/src/frontend.ts (lines 1216 resolveGrants called once; 849-866 mintAccessToken reads baked grants; 838-847 grantsForOrg; 1303-1334 mint handler never re-resolves)

CALL COUNT:
1 resolution site (finishSignIn) feeding all mint sites; 2 mint paths (token mint, org switch) reuse the baked grants.

FIX:
* Root cause: grants are cached at sign-in with no refresh.
* How: add an optional re-resolution on mint and/or a max grant-age.
* Structure: allow createFederatedFrontend to take a `reresolveGrantsEverySeconds` (and/or a `revalidate(identity)` callback). On mint, if the session's grants are older than that window, re-run resolveGrants (or a lighter membership check) and update the record; if the user no longer qualifies, treat as signed out.
* Files changed: frontend.ts (thread a grant-age timestamp onto the session record; re-resolve in handleMintToken before minting; expire on failure). Document that embedded deployments must set a short inactivity timeout + a store, or a grant-refresh window, to bound deprovision latency.

3. Session-store read failure fails OPEN — falls back to the signed cookie and bypasses revocation / inactivity / max-lifetime  [MEDIUM]

SITUATION / PROBLEM:
In stateful mode, readSession looks up the durable record to enforce revocation, max-lifetime, and inactivity. If the store read THROWS, the catch logs a warning and returns the cookie-derived record (cookieRec) — i.e. it treats the request as fully signed in, skipping every store-side check. A revoked or aged-out user whose store read errors regains access.

ROOT CAUSE:
The fault handler prioritizes availability over the security checks the store exists to enforce ("a transient filesystem error must not lock the user out").

SCENARIO:
An operator revokes a compromised user (tombstone written). Shortly after, the disk fills or the sessions directory permissions change, so store.get() throws. The revoked user's still-valid cookie now sails through readSession's catch branch as a live session — revocation is silently defeated for the duration of the fault. An attacker who can induce store errors (fill the volume, exhaust file handles) can convert "revoked" back into "active".

RISK:
Revocation and inactivity/expiry are bypassable under fault, including attacker-inducible fault. Impact medium-high (defeats the store's whole purpose exactly when it matters); likelihood low-moderate.

REPRO STEPS:
1. Configure a FileSessionStore; sign in; revoke the session (tombstone).
2. Make store.get throw (e.g. chmod 000 the sessions dir, or fill the disk).
3. Request /client with the still-present cookie.
4. Observe a signed-in snapshot despite the tombstone.

SOURCE FILES INVOLVED:
/Users/bryan/BGit/Bryan_git/OpenAuthFederated/code/packages/auth-backend/src/frontend.ts (lines 799-803 catch → returns cookieRec)

CALL COUNT:
1 (readSession catch), but readSession backs every authenticated endpoint (/client, mint, touch, remove, reverify).

FIX:
* Root cause: fail-open on store error.
* How: make the failure mode configurable and default to fail-closed for security-critical reads, with a bounded grace only for genuinely transient errors.
* Structure: add `sessionStoreFailMode: "closed" | "cookie-grace"` (default "closed"). In "closed", a store error returns null (signed out). Optionally allow a very short grace window keyed off cookie iat for availability-sensitive apps, but never an unbounded fallback.
* Files changed: frontend.ts (replace the blanket cookieRec fallback with the configured behavior; keep the warning log).

4. Revocation, "sign out everywhere", and inactivity timeout are silent no-ops unless the app opts into a sessionStore  [MEDIUM]

SITUATION / PROBLEM:
The durable store is optional. In the default stateless mode, handleRemove only clears the session cookie in the current browser; there is no server-side record to tombstone, so a copied/stolen cookie remains valid until its exp. The inactivity timeout is likewise "only enforced when a sessionStore is set", and the active-sessions list returns empty. An app that never wires a store believes it has logout + idle-timeout + revocation, but has none of them server-side.

ROOT CAUSE:
The stateful half of the session model is opt-in and easy to omit; the stateless default looks fully functional in the happy path (the local cookie clears) so the missing server-side revocation is invisible in normal testing.

SCENARIO:
A laptop is stolen with a live session cookie. IT clicks "sign out" in the admin app — but the app never configured a store, so the click cleared the cookie only in IT's browser. The stolen cookie keeps working until its multi-day exp.

RISK:
No true revocation / logout-everywhere / idle timeout by default. Impact high on incident response; likelihood moderate (many apps skip the store).

REPRO STEPS:
1. createFederatedFrontend without sessionStore.
2. Sign in, copy the oaf_session cookie to a second browser.
3. Call /client/sessions/:id/remove from browser 1.
4. Browser 2's copied cookie still authenticates.

SOURCE FILES INVOLVED:
/Users/bryan/BGit/Bryan_git/OpenAuthFederated/code/packages/auth-backend/src/frontend.ts (lines 1401-1420 handleRemove; 733-804 readSession store branch; 607-613 defaults; 1427-1452 list)

CALL COUNT:
Structural default; affects logout, revocation, idle-timeout, and session-listing across the whole Frontend API.

FIX:
* Root cause: security-critical controls gated behind an easily-missed opt-in.
* How: make a durable store the default, or fail loudly when one is absent but revocation/idle features are used.
* Structure: default sessionStore to a FileSessionStore rooted at a required data dir; or emit a construction-time warning ("no sessionStore: sign-out is local-only, idle timeout disabled, revocation unavailable") and document it prominently.
* Files changed: frontend.ts normalizeConfig (default or warn); README/docs.

5. sessionStoreMigrate can resurrect a revoked session from a still-valid cookie  [MEDIUM]

SITUATION / PROBLEM:
When sessionStoreMigrate is true, readSession, on finding NO durable record for a valid cookie's sid, re-creates the record from the cookie (createdAt/expireAt taken from the JWT). Tombstones are normally what stop this, but if a tombstone file is lost (manual cleanup, disk rotation, backup restore that predates the revocation), the migration path treats "no record" as "new user" and rebuilds an active session from the attacker's/ex-user's still-valid cookie.

ROOT CAUSE:
The migration branch cannot distinguish "never had a record" from "record was revoked then deleted"; it trusts the cookie.

SCENARIO:
A revoked user's tombstone is pruned by a cleanup job. Their old cookie (still within max lifetime) is replayed while migrate is on → readSession recreates a non-revoked record → access restored.

RISK:
Revocation reversal in the presence of tombstone loss. Off by default, so impact depends on adoption; medium where migrate is enabled.

REPRO STEPS:
1. Enable sessionStoreMigrate. 2. Sign in, revoke (tombstone), then delete the tombstone file. 3. Replay the cookie → session is rebuilt as active.

SOURCE FILES INVOLVED:
/Users/bryan/BGit/Bryan_git/OpenAuthFederated/code/packages/auth-backend/src/frontend.ts (lines 785-796 migration recreate)

FIX:
* Root cause: cookie-trusting migration cannot see prior revocation.
* How: bound migration to a one-time window and/or require a positive "not previously revoked" signal; never migrate a sid older than a short cutoff.
* Files changed: frontend.ts (gate the migrate branch by cookie-age cutoff and a persisted migration-complete marker per user).

6. Google id_token verification does not pin `algorithms` (inconsistent with every other verify path)  [LOW]

SITUATION / PROBLEM:
Every other jwtVerify call in the library pins `algorithms` (HS256 for internal cookies/tokens, RS256 on the JWKS path). The Google id_token check in handleCallback passes only `{ issuer, audience }` — no `algorithms: ['RS256']`.

ROOT CAUSE:
Missing algorithms option on this one call.

SCENARIO:
Low practical risk because the key comes from Google's JWKS (an RSA public key), so jose will not HMAC-verify with it; but the inconsistency removes the defense-in-depth every other path has and would matter if the keyset resolution ever changed.

RISK:
Defense-in-depth gap / inconsistency. Low.

8. SAML response-envelope signature is off by default (residual XML Signature Wrapping exposure)  [LOW]

SITUATION / PROBLEM:
wantAuthnResponseSigned defaults to false (Google signs the assertion, not always the response). Requiring only the assertion signature is the weaker XSW posture. It is mitigated here by node-saml v5 signature-reference hardening, the audience check, InResponseTo (ifPresent), and the assertion-id replay cache — but response-envelope signing is the strongest single XSW defense and is not on by default.

SOURCE FILES INVOLVED:
/Users/bryan/BGit/Bryan_git/OpenAuthFederated/code/packages/auth-backend/src/saml.ts (lines 46-54, 82-114)

FIX:
Keep the default but document loudly that IdPs which sign the response should set wantAuthnResponseSigned: true; consider defaulting true and letting Google-only deployments opt out.

10. assertSafeIssuer permits ANY https host when no jwksAllowedHosts allowlist is supplied (SSRF if issuer is ever caller/tenant-derived)  [LOW]

SITUATION / PROBLEM:
On the production JWKS path, assertSafeIssuer requires https + a real host but, when jwksAllowedHosts is empty, allows any host. The issuer becomes an outbound fetch to `<issuer>/.well-known/jwks.json`. Issuer is normally app-configured (low risk), but any app that derives issuer from per-tenant/user input without setting an allowlist gets an SSRF primitive to internal https services.

SOURCE FILES INVOLVED:
/Users/bryan/BGit/Bryan_git/OpenAuthFederated/code/packages/auth-backend/src/verify.ts (lines 105-119, 178-186)

FIX:
Recommend (or require) jwksAllowedHosts whenever issuer is not a compile-time constant; optionally block private/link-local IP literals even when the allowlist is empty.

11. Oversized request-body guard resolves early but keeps buffering the stream (memory DoS)  [LOW]

SITUATION / PROBLEM:
readJsonBody / readFormBody guard oversized bodies by calling finish({}) once data exceeds the cap, but they do not remove the 'data' listener or destroy the request, so `data` keeps growing on the closure until the stream ends. A slow, large upload continues consuming memory after the promise has resolved.

SOURCE FILES INVOLVED:

FIX:
On exceeding the cap, `req.destroy()` (or remove listeners) so buffering actually stops; keep the early resolve.

SITUATION / PROBLEM:
redactEmail logs `user_<sha256(email)[:12]>@domain`. This is good PII minimization, but the hash is unsalted and truncated over a lowercased email, and the plaintext domain is retained. If logs leak, an attacker can confirm whether a guessed email signed in (hash it and match) and see which company domains are in use.

SOURCE FILES INVOLVED:
