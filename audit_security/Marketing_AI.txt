================================================================================
SECURITY AUDIT REPORT — "Marketing AI"
================================================================================

Scope: Marketing AI web app (~/BGit/all/marketing/ai). Audited everything under
/code (Express + TypeScript backend in code/src, vanilla-JS UI in code/ui) and
the paired CLI under /cli that authenticates to the same API. Focus: (a) app-side
security bugs and (b) incorrect usage of the embedded OpenAuthFederated auth
library (@auth/backend + the browser access-token helpers). Library source of
truth read at: ~/BGit/Bryan_git/OpenAuthFederated/code/packages/*/src.

Overall: This app is unusually well hardened. A prior audit pass (referenced in
code as "Audit finding N") already closed the high-impact issues — single
default-deny /v1 boundary, CORS allowlist (no credentialed wildcard), HMAC raw-
body webhook verification, issuer+audience token binding enforced on BOTH mint
and verify, least-privilege resolveGrants, CSRF origin checks on cookie auth,
Secure-cookie-tracks-transport, distinct cookiePrefix (oaf_mai), a durable
FileSessionStore for revocation, loopback-only + file-hash CLI bootstrap disabled
in server mode, and no forked/decode-only token verification. The findings below
are the residual weaknesses that remain after that hardening.

One-line summary: 6 findings — 0 CRITICAL, 1 HIGH, 1 MEDIUM, 4 LOW.

1. Bearer access token persisted to browser localStorage  [HIGH] [MISUSE]

SITUATION / PROBLEM:
The browser UI copies the master-signed Bearer ACCESS TOKEN into
window.localStorage under the key "mai.token", and reads it back from
localStorage on load. The OpenAuthFederated front-end contract is explicit: the
access token is kept IN MEMORY only; the durable credential is the HttpOnly
rotating cookie. Apps MUST NOT copy tokens into localStorage/sessionStorage,
because localStorage is readable by any JavaScript running on the origin — so a
single XSS (or a malicious/compromised dependency, or a browser extension with
page access) can exfiltrate a valid API bearer at will, and the token also
survives tab close and lingers after navigation.

ROOT CAUSE:
setToken() writes the minted JWT to localStorage on every mint, and getToken()
falls back to reading it from localStorage. The in-memory `state.token` was meant
to be the whole store; localStorage persistence was bolted on top of it.

  code/ui/lib/auth.js:
    - MAI_TOKEN_KEY = 'mai.token'                                    (line ~26)
    - getToken(): `state.token = localStorage.getItem(MAI_TOKEN_KEY)`(lines ~58-62)
    - setToken(tok): `localStorage.setItem(MAI_TOKEN_KEY, tok)`      (lines ~65-73)
    - ensureAccessToken(): `setToken(jwt)` after minting            (line ~121)

SCENARIO:
An attacker lands a stored-XSS payload anywhere the UI renders untrusted content
(this is a marketing/knowledge-ingestion app that stores scraped social posts,
topics, and AI-proposed copy — a large untrusted-content surface). The payload
runs `localStorage.getItem('mai.token')`, ships the JWT to an attacker origin,
and the attacker replays it as `Authorization: Bearer <jwt>` against /v1/* for
the token's lifetime — as the victim, at the victim's permission level.

RISK:
Token theft → full API impersonation of the victim (including an admin if the
victim is admin). Mitigations that reduce but do not remove the risk: the access
token is short-lived (AUTH_ACCESS_TOKEN_TTL_SECONDS default 900s) and the session
cookie itself is HttpOnly (XSS cannot read the cookie directly). But the contract
prohibits stored bearers precisely because a stored token is a standing,
directly-readable credential rather than an ephemeral in-memory one.

REPRO STEPS:
1. Sign in to http://localhost:7700 with an allowed-domain Google account.
2. In DevTools console: `localStorage.getItem('mai.token')` → returns a JWT.
3. From any other context: `curl -H "Authorization: Bearer <that-jwt>"
   http://localhost:7700/v1/auth/me` → 200 with the victim's identity.

SOURCE FILES INVOLVED:
  App:     ~/BGit/all/marketing/ai/code/ui/lib/auth.js (lines ~26, ~58-73, ~121-131)
  Library: ~/BGit/Bryan_git/OpenAuthFederated/code/packages/auth-react/src/core.ts
           and hooks.ts (define the in-memory + HttpOnly-cookie model the app must
           follow; the app bypasses it with its own vanilla-JS helper)

CALL COUNT:
getToken()/setToken() are used throughout ui/lib/auth.js (ensureAccessToken,
probeWhoami, signOut) and by ui/lib/api.js on every API call and on 401 re-mint.

FIX (root cause):
Keep the access token in a module-scoped variable ONLY; never touch localStorage.
- App: in code/ui/lib/auth.js delete MAI_TOKEN_KEY and both localStorage calls;
  getToken() returns `state.token` (in-memory) only; setToken() sets `state.token`
  and notifies, with no persistence. On load there is no token — call
  ensureAccessToken() (which mints from the HttpOnly cookie) to repopulate it.
  This matches the library's memory-plus-rotating-cookie model exactly and loses
  no functionality (the cookie already survives reload).
- Library: no change required; the model is already correct.

2. Session lifetime + inactivity timeout set to 10 months  [MEDIUM] [MISUSE]

SITUATION / PROBLEM:
The app configures the embedded library with a 10-month (300-day, 25,920,000 s)
session TTL AND a 10-month inactivity timeout. The library default is 7 days.
The library contract flags years-long sessionTtl values as a weakener of
captured-session risk: a stolen/copied session cookie stays valid far longer, and
the inactivity timeout being equal to the max lifetime means an idle or abandoned
session is effectively never expired by inactivity.

ROOT CAUSE:
A product requirement ("stay signed in for 10 months, never logged out on idle or
restart") was implemented by setting both ceilings to 10 months.

  code/src/lib/config.ts:
    - SESSION_TTL_SECONDS = 60*60*24*30*10  (= 25,920,000 s)        (lines ~340-342)
    - AUTH_INACTIVITY_TIMEOUT_SECONDS = 60*60*24*30*10              (lines ~346-348)
  code/src/lib/auth_frontend.ts:
    - sessionTtlSeconds: SESSION_TTL_SECONDS                        (line ~835)
    - inactivityTimeoutSeconds: AUTH_INACTIVITY_TIMEOUT_SECONDS     (line ~837)

SCENARIO:
A laptop is lost, a browser-profile backup leaks, or a session cookie is
exfiltrated. Because there is no inactivity expiry short of 10 months, that
session remains usable for the better part of a year unless an operator manually
revokes it through the session store.

RISK:
Extended window for captured-session abuse. Partly mitigated: a durable
FileSessionStore IS wired up (auth_frontend.ts line ~841), so an admin CAN
force-revoke, and short (15-min) access-token TTL limits the Bearer window — but
the long-lived cookie can always mint fresh access tokens for 10 months.

REPRO STEPS:
1. Sign in; copy the oaf_mai_session cookie value.
2. Leave the session idle for any period short of 10 months.
3. Present the cookie to the SPA mint endpoint — it still mints access tokens.

SOURCE FILES INVOLVED:
  App:     ~/BGit/all/marketing/ai/code/src/lib/config.ts (lines ~340-348)
           ~/BGit/all/marketing/ai/code/src/lib/auth_frontend.ts (lines ~835, ~837)
  Library: ~/BGit/Bryan_git/OpenAuthFederated/code/packages/auth-backend/src/frontend.ts
           and session-store.ts (consume sessionTtlSeconds / inactivityTimeoutSeconds)

CALL COUNT: 1 configuration site (buildAuthFrontend), 2 constants.

FIX (root cause):
Decouple the two ceilings. Keep a long absolute max if the product truly needs it,
but set inactivityTimeoutSeconds much shorter (e.g. 7-14 days) so idle/abandoned
sessions expire while active users still roll forward via the sliding window.
- App: in config.ts lower AUTH_INACTIVITY_TIMEOUT_SECONDS to e.g. 14 days and
  consider capping SESSION_TTL_SECONDS to 30-90 days; document the tradeoff.
- Library: no change (it already honours both values via the session store).

3. Terminal error handler leaks internal error messages to clients  [LOW] [APP-BUG]

SITUATION / PROBLEM:
The final Express error handler returns the raw exception message to the caller as
JSON. Internal error text (DB driver errors, file paths, stack-adjacent messages)
aids reconnaissance and can disclose implementation detail.

ROOT CAUSE:
Convenience handler echoes err.message instead of a canonical opaque envelope.

  code/src/server.ts:
    app.use((err,_req,res,_next) => { res.status(500).json({ error: err.message }) })
                                                                    (lines ~579-581)
  Same pattern at the space-algo-ai start route: res.status(500).json({ ok:false,
  error: message }) where message = error.message                  (lines ~530-531)

SCENARIO:
Any request that trips an unhandled exception (bad input reaching a DB call, a
filesystem error) returns the internal message verbatim to the client.

RISK:
Information disclosure. Low: most routes already use the canonical error envelope
(api_contract), the DB errors are Postgres-side, and there is no auth bypass.

REPRO STEPS:
1. Trigger any route that throws below the canonical handlers.
2. Observe the raw driver/exception text in the 500 JSON body.

SOURCE FILES INVOLVED:
  App: ~/BGit/all/marketing/ai/code/src/server.ts (lines ~530-531, ~579-581)

CALL COUNT: 1 global handler + 1 route handler.

FIX (root cause):
Return a fixed opaque message plus a correlation id (X-Request-Id is already set by
requestIdMiddleware); log the real error server-side via logError. Replace
`{ error: err.message }` with `{ error: { code: 'internal', requestId } }`.
- App only; no library change.

4. Process-spawn launch endpoints reachable by any signed-in user  [LOW] [APP-BUG]

SITUATION / PROBLEM:
POST /v1/launch/space-algo-ai/start spawns `npm run dev` in another repo. It sits
behind the /v1 default-deny auth boundary (good) but is NOT restricted to admins,
so any authenticated identity — including a least-privilege read-only "member"
(the default grant from resolveGrants) — can start a detached server process on
the host.

ROOT CAUSE:
The launch routes are registered after the requireAuth boundary but without a
requireAdmin guard, unlike the other operational surfaces (admin/audit/settings
all use requireAdmin).

  code/src/server.ts:
    app.post('/v1/launch/space-algo-ai/start', ... spawn('npm',['run','dev'], ...))
                                                                    (lines ~507-533)
  Boundary that protects it: app.use('/v1', ... requireAuth ...)   (lines ~353-361)

SCENARIO:
A signed-in non-admin employee (or a stolen non-admin token per finding 1)
repeatedly POSTs the start endpoint, launching processes / consuming host
resources.

RISK:
Low: fixed argv (no command injection — not user-controlled), same-host only,
requires a valid company-domain session, and it no-ops if the port is already
serving. Impact is resource/process control by a non-admin.

REPRO STEPS:
1. Sign in as a non-admin allowed-domain user; mint an access token.
2. POST /v1/launch/space-algo-ai/start → a detached `npm run dev` is spawned.

SOURCE FILES INVOLVED:
  App: ~/BGit/all/marketing/ai/code/src/server.ts (lines ~502-533)

CALL COUNT: 2 launch routes (check + start).

FIX (root cause):
Gate the start (and arguably check) routes with requireAdmin, matching the other
operator surfaces. Register them via a router that applies requireAdmin, or wrap
the handler with requireAdmin.
- App only; no library change.

5. "Clerk" reference in source comment (charter naming violation)  [LOW] [MISUSE]

SITUATION / PROBLEM:
The OpenAuthFederated charter forbids naming the commercial identity provider
being modeled ("never use ... in code, comments, documentation ...; output
warnings if you find anything"). A source comment names it.

ROOT CAUSE:
Explanatory comment drew an analogy to the commercial product by name.

  code/ui/lib/auth.js line 10:
    " * API middleware. This mirrors Clerk's getToken(): the cookie is the session,"

SCENARIO / RISK:
No runtime security impact. It is a charter/compliance violation that must be
scrubbed; this report raises the required warning.

REPRO STEPS:
grep -niw "clerk" code/ui/lib/auth.js → one hit at line 10. (No other
word-boundary hits for clerk/clark exist in code/src, code/ui, cli/src, cli/bin.)

SOURCE FILES INVOLVED:
  App: ~/BGit/all/marketing/ai/code/ui/lib/auth.js (line 10)

CALL COUNT: 1 comment.

FIX (root cause):
Reword generically, e.g. "This mirrors a hosted identity provider's getToken():
the cookie is the session, the short-lived access token is the API credential."
- App only.

6. Over-broad startsWith prefix matching on the /v1 public allowlist  [LOW] [APP-BUG]

SITUATION / PROBLEM:
The /v1 default-deny boundary whitelists public prefixes with a plain
`p === pre || p.startsWith(pre)` test. Because entries like '/config',
'/manifest', '/ingest', and '/local-api-key' are matched by startsWith, any
FUTURE route whose path merely begins with one of those strings (e.g.
'/configuration', '/manifests-internal', '/ingest-admin') would be silently
exposed without authentication.

ROOT CAUSE:
Prefix membership test is not anchored to a path-segment boundary.

  code/src/server.ts:
    const V1_PUBLIC_PREFIXES = ['/config','/manifest','/ingest/','/ingest',
      '/local-api-key','/auth/','/auth']                            (line ~352)
    ... V1_PUBLIC_PREFIXES.some((pre) => p === pre || p.startsWith(pre)) (line ~356)

SCENARIO:
Latent, not currently exploitable — no existing route has such a name. Becomes a
real unauth exposure the day someone adds a route whose name shares a prefix.

RISK:
Low today (no matching route exists); the impact is a foot-gun that turns a new
route public by accident.

REPRO STEPS:
Static review: add a hypothetical GET /v1/configXYZ handler after the boundary →
it is reachable anonymously.

SOURCE FILES INVOLVED:
  App: ~/BGit/all/marketing/ai/code/src/server.ts (lines ~352-361)

CALL COUNT: 1 boundary.

FIX (root cause):
Match on exact path or a trailing-slash segment boundary: allow when
`p === pre || p.startsWith(pre.endsWith('/') ? pre : pre + '/')`. Keep the
already-correct '/ingest/'-style entries; drop the bare-prefix ambiguity.
- App only; no library change.
